# 单路高清、多路低码率预览（v1.4.0）

配套地面站为 v1.01.11-adaptive-rc1。只需保留“云台方案”和“算法板方案”：手动开启且可见的视频为一路时请求原高清地址，两路以上请求同名 `_low` 地址。单路全屏暂停其他路，使用高清；退出恢复原选择和低清。设置中仍保留高清地址，录像仍从原高清地址保存。

## 按需启停

主控在 RTSP DESCRIBE/SETUP 阶段触发低清输出，PLAY 后续租；普通播放请求已经包含所需信息，不额外增加地面端控制协议。主控每秒通过板间有线 UDP 续租。最后一个客户端正常退出后，不再续租，约 5～6 秒释放低清编码器和帧缓冲。异常断网还需等待 RTSP 控制连接/会话超时。暂停、关闭、多人同时观看和重新打开均按各路订阅独立处理。

源端只接受配置的有线主控 IP 的固定租约消息，不使用跟踪 TCP 9000/9001，也不在主控先解码高清再转码。新增源码 `board/src/low_stream.c`；3588 使用 MPP/RGA，3576 云台使用同一工作线程和 `gimbal/rockit_low_encoder.c` 的厂家 Rockit/VENC 适配。云台原两个通道保持一套程序，不拆进程。

## 安装与升级范围

新主控和新算法板纯视频角色沿用根目录/algorithm 安装命令，安装包中的编码程序已支持低清并配置独立开机服务。现有主控可在完整 v1.4.0 包中运行 `sudo python3 update_low_streams.py`，它备份数据盘、保留当前模式和网络、只重启相关视频组件。

已有 TTTracker 算法板不能拿纯视频二进制覆盖：必须把 `low_stream.c/h` 接入该板现有 `streamer.c`，在编码前后的完整 NV12 帧调用 create/offer/destroy，重新链接原 `tracker_tt.cpp`，保留该板 tracker_worker、IPC 头及静态算法库。104 所连算法板已单独完成此步骤。环境需设置 `UAV_LOW_ENABLE=1`、`UAV_LOW_BIND=192.168.10.2`、`UAV_LOW_PEER=192.168.10.1`，其低清线程使用 `UAV_LOW_CPUS=0-3`。旋转参数使用本机原配置。

云台需使用相同算法版本的低清适配程序，并在原启动入口增加 `UAV_LOW_ENABLE=1`、`UAV_LOW_BIND=192.168.144.108`、`UAV_LOW_PEER=192.168.144.1`、`UAV_LOW_CPUS=0-3`。当前云台已配置。旧载荷程序只有高清输出，不能仅升级地面站便宣称低清可用。

## 验证范围与回退

2026-10-21：六路实际相机的高清和低清均解码成功；六路低清同时复制压缩码流约 25 秒，每路约 381 帧，视频载荷合计约 3.28Mbps。主控整板 CPU 短采样约 8.6%→10.6%，云台约 11.1%→12.4%；算法板采样约 15.7～19.4%，受场景和调频影响，不能把采样下降当成性能提升。原高清前视及云台可见光仍约 30fps，云台红外约 25fps。无人观看后新增编码器释放。

模拟源验证覆盖未订阅时不创建编码器、多客户端共享、关闭其中一个后另一个继续、最后退出释放与重新打开。没有替代室外 MK22 无线距离验收，也未完成数小时热稳定性测试。
